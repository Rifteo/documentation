## Purpose

This guide defines the rules every contributor must follow when writing skill documentation. Consistent style makes the community hub trustworthy and easy to navigate, especially for teams adopting AuditGuard across different projects.

---

## Tone and voice

| Do | Don't |
|----|-------|
| Use plain, direct language | Use jargon without explanation |
| Write in second person ("you") | Write in first person ("I", "we") |
| Be specific about what something does | Write vague filler like "provides a way to" |
| State limitations honestly | Oversell or omit known gaps |

**Good:** "This skill checks whether all user accounts have MFA enabled." 
**Bad:** "This skill helps you improve your security posture by leveraging best practices."

---

## Page structure rules

Every skill page must include these sections in this order:

1. Frontmatter (`title`, `description`)
2. One-sentence summary (below the title, before any heading)
3. `<Info>` block with status, version, author, tags
4. **What it checks**: scope and out-of-scope
5. **Inputs**: parameter table
6. **Output**: status table + JSON examples
7. **Usage**: CLI command
8. **Example**: realistic command + output
9. **Known limitations**
10. **Changelog**

No section may be left empty. If there are no known limitations, write "None at this time."

---

## Writing rules

### Headings

- Use sentence case: `## What it checks` not `## What It Checks`
- Do not skip heading levels (no jumping from `##` to `####`)
- Keep headings short, describe don't explain

### Code blocks

- Always specify the language for syntax highlighting: ` ```bash `, ` ```yaml `, ` ```json `
- Show realistic values in examples, not `foo` / `bar` placeholders
- Show the full command, including the `auditguard` prefix

### Tables

- Always include a header row
- Keep cell content under 80 characters
- Use inline code `` `value` `` for exact values, types, and field names

### Lists

- Use bullet lists for unordered items
- Use numbered lists only for sequential steps
- Keep each item to one sentence
- Do not mix bullets and sub-bullets more than one level deep

## Frontmatter requirements

Every `.mdx` file must start with:

```yaml
---
title: <Page title, sentence case, under 60 chars>
description: <One sentence describing the page, shown in search results>
---
```

The `description` field appears in search results and navigation previews. Make it informative, not generic.

**Good:** `"Checks whether all IAM users have MFA enabled, per SOC 2 CC6.1."` 
**Bad:** `"Documentation for the MFA skill."`

---

## Status tags

Use the `<Info>` block at the top of every skill page with these exact fields:

```mdx
<Info>
 **Status:** Draft | Review | Stable 
 **Version:** 1.0.0 
 **Author:** your-name 
 **Tags:** compliance, security, access, data
</Info>
```

**Status definitions:**

| Status | Meaning |
|--------|---------|
| `Draft` | Work in progress, do not use in production |
| `Review` | Ready for team review, pending approval |
| `Stable` | Reviewed, approved, and safe to use |

---

## Approved tags

Only use tags from this list to ensure consistent filtering:

| Tag | Use for |
|-----|---------|
| `compliance` | Checks tied to a compliance framework (SOC 2, ISO 27001, etc.) |
| `security` | General security controls and vulnerability checks |
| `access` | Identity, permissions, and access control checks |
| `data` | Data handling, retention, and classification checks |
| `infrastructure` | Cloud, network, and system configuration checks |
| `process` | Workflow, approval, and operational procedure checks |

---

## What NOT to write

- Do not explain how Python works
- Do not summarize what you just wrote in a closing paragraph
- Do not add headings with no content under them
- Do not repeat the skill name in every sentence
- Do not write "this skill" more than twice per section, use "it" after the first mention

---

## Checklist before submitting

Run through this before opening your PR:

- [ ] All required sections are present and non-empty
- [ ] Frontmatter has both `title` and `description`
- [ ] `<Info>` block has all four fields
- [ ] Code blocks have language identifiers
- [ ] Example shows a realistic command and realistic output
- [ ] Known limitations are documented
- [ ] No placeholder text (`<fill this in>`, `TODO`, `TBD`) remains
